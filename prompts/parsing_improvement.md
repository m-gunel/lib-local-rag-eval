# Задача: улучшить парсинг файлов в индексаторе lib-local-rag

Работаем в режиме планирования. Сначала изучи код и проверь диагноз ниже на реальных файлах, потом предложи план. Код проекта не меняй, пока я не согласую план. Отвечай по-русски и простыми словами: если используешь термин, коротко поясни его.

## 1. Контекст

**Проект.** lib-local-rag — локальный индексатор для SberOS: индексирует папки пользователя (pdf, docx, doc, pptx, xlsx, xls, txt) и ищет по ним через `POST /api/v1/search` — гибридный поиск BM25 + векторы, топ-10 документов. Правила сборки и «грабли» проекта — в `AGENTS.md`, он подгружается автоматически.

**Копии проекта.** Их две, обе без git, парсеры в них одинаковые:
- `~/Downloads/lib_local_rag` — на ней делался замер качества;
- `~/Downloads/lib-local-rag-s` — база для сборки deb-пакета, в ней есть `.venv` с python, ruff и pytest.

Прежде чем что-то менять, уточни у меня, в какой копии работаем, и предложи, как сохранить исходное состояние (резервная копия или `git init`).

**Что уже сделано.** Качество ранжирования замерено на отдельном стенде `~/Downloads/lib-local-rag-eval` (приватный репозиторий `git@github.com:m-gunel/lib-local-rag-eval.git`, порядок работы — в его `README.md`):
- итоговая сводка — `reports/summary.md`;
- полные отчёты — `reports/R6.md` (индексатор как есть) и `reports/R7.md` (полный индекс);

Парсинг — один из четырёх пунктов улучшения. Остальные три — потеря чанков при первичной индексации, веса в гибридном поиске и модель эмбеддингов — в этом чате не трогаем.

## 2. Как устроен парсинг сейчас

- `src/parsers/` — парсер на каждое расширение, реестр `@parser(...)` в `base.py`. Каждый парсер отдаёт `Chunk(idx, text)`.
- pdf, docx, pptx, txt собирают весь текст файла в одну строку и режут её `self._config.embed_splitter`: `RecursiveCharacterTextSplitter`, 500 токенов с перекрытием 100, длина считается токенизатором модели через `count_tokens`.
- xlsx: одна строка листа = один чанк, без нарезки, формат задаёт шаблон `templates/excel_row.j2`.
- `src/parsers/__init__.py`, `_process_path`: исключение при разборе → `fail_cb(permanent=False)`, файл перечитывается на каждом проходе; ноль чанков → `fail_cb(permanent=True)`, файл помечается пустым навсегда.
- Полнотекстовый индекс строится только по полю `text` чанка (`src/utils/lance_wrapper.py`, `create_fts_index(field_names="text", tokenizer_name="ru_stem")`). Вектор тоже считается только по тексту чанка. Название файла (`meta.original_name`) в поиске не участвует, оно лишь показывается в ответе (`src/server/model.py`).

## 3. Диагноз: что найдено и чем подтверждено

Цифры получены на корпусе стенда: 400 документов, 43 617 чанков. Готовые чанки текущих парсеров по каждому документу лежат в `work/indexer_view_corpus/<набор>__<файл>.chunks.json`.

**xlsx** (`src/parsers/xlsx.py`) — худший результат замера: Hit@10 = 0,18, с полным индексом 0,27, всего 55 запросов.
- Заголовок таблицы — одна строка из первых 15, выбранная эвристикой `_analyze_header_patterns` с порогом 0,3. На листе «1» файла `corpus/cbr_stat/Статистические показатели банковского сектора obs_287.xlsx` выбрана строка «Раздел I. Общие сведения…», а настоящий заголовок с датами стоит в строке 4.
- Двухуровневые заголовки и объединённые ячейки превращаются в `Column_4`, `Column_6`.
- Шаблон `templates/excel_row.j2` выводит только пары «столбец: значение». `sheet_name` в него передаётся, но не используется, названия таблицы в чанке нет.
- Даты выводятся как `2025-01-01 00:00:00`, числа без округления: `463.76610400000004`.
- `_should_skip_sheet` выбрасывает лист целиком, если в первых 50 строках меньше 10% текстовых ячеек. В obs_287 так пропали 3 листа из 24: таблицы 2, 11 и 22, в том числе «Размещение и активы кредитных организаций по регионам».
- Лимиты: `ExcelParserConfig.max_rows = 1000` (дальше строки обрезаются), лист длиннее 5000 строк пропускается весь.
- `.xls` зарегистрирован на этот же парсер, но openpyxl его не читает (`InvalidFileException`), поэтому файл падает на каждом проходе.
- Пример — запрос `xl000`: «Сколько внутренних структурных подразделений банков работало в Челябинской области на 1 января 2025 года?», ответ 613. Правильными считаются все 8 выпусков статистики. Чанк из `obs_280.xlsx`:
  ```
  Федеральный округ: Челябинская область
  2024-01-01 00:00:00: 637
  Column_4: 169
  2025-01-01 00:00:00: 613
  ```
  Слов «внутренние структурные подразделения» в чанке нет, и неясно, какое из чисел — ответ.

**Контекст документа в чанках** — затрагивает все форматы, сильнее всего сценарий «выбор среди похожих документов» (453 запроса):
- название банка есть лишь в 20% чанков МСФО-отчётов, год — в 54%;
- на вопрос про Альфа-Банк за 2022 год первым выходит отчёт Совкомбанка за 2022-й.

**PDF** (`src/parsers/pdf.py`: `"\n".join(page.get_text() for page in doc)`, вариант с `pymupdf4llm` закомментирован):
- переносы рвут слова: регулярка `[а-яёa-z][­‑\-‐]\s*\n\s*[а-яёa-z]` находит 84 505 разрывов в 21 746 чанках актов ЦБ, почти 4 на чанк;
- мягкий перенос U+00AD встречается в 5% чанков актов;
- колонтитул «ВЕСТНИК БАНКА РОССИИ» — в 14% чанков актов. Тексты актов вырезаны из выпусков «Вестника», поэтому решение должно быть общим — искать повторяющиеся строки по страницам, — а не под этот колонтитул;
- таблицы рассыпаются: подписи и числа идут отдельными строками, заголовков столбцов в чанке нет, числа разбиты пробелами («27 821,6»). Пример — баланс в `Сбербанк МСФО 2024 годовая.pdf`;
- нет OCR: скан даёт ноль текста и навсегда помечается пустым. В корпусе это 3 отчёта из 52 (31 запрос исключён из замера).

**pptx** (`src/parsers/pptx.py`: только `getattr(shape, "text")` для фигур верхнего уровня):
- таблицы, сгруппированные фигуры и заметки докладчика пропускаются;
- в 23 презентациях ZX Bank парсер взял 68 088 символов из 90 774 (75%), выпали все 51 таблица; в 10 файлах потеряно больше 20%, например «сеть отделений в Дели» — 710 символов из 4436 (выпали адреса и телефоны);
- на документных метриках это почти не видно — документ находится по заголовку. Но ответа в индексе нет, а для RAG и MCP это важно.

**docx** (`src/parsers/docx.py`, `docx2txt.process`):
- автонумерация пунктов теряется («1.», «2.1» исчезают — проверено на docx, собранном pandoc);
- таблицы рассыпаются по одной ячейке на строку.

**txt:** `decode("utf-8", errors="replace")` — файл в Windows-1251 превращается в `�`.

**doc:** нужен внешний конвертер (textutil, catdoc, antiword или soffice). Если на SberOS его нет, файл тихо пропускается. Наличие конвертера на SberOS не проверено.

## 4. Предлагаемый порядок — проверь и обоснуй свой

1. **Контекст документа в чанках** и поиск по названию файла или документа. Это самое широкое влияние: все форматы и сценарий 5. Вопрос устройства: приклеивать заголовок к тексту чанка (он съедает часть бюджета в 500 токенов) или хранить отдельным полем — попадёт ли оно тогда в полнотекстовый индекс по нескольким полям в lancedb 0.38 и в вектор?
2. **xlsx:** заголовки, включая многоуровневые и объединённые ячейки; название таблицы и листа в каждом чанке; даты и числа в читаемом виде; не выбрасывать числовые листы; пересмотреть лимиты строк.
3. **PDF, очистка текста:** склейка переносов, удаление мягких переносов, удаление повторяющихся колонтитулов и номеров страниц. Таблицы PDF (например, `page.find_tables()` или pymupdf4llm) и OCR — отдельные решения со своими рисками по зависимостям и скорости: вынеси их в план отдельными пунктами.
4. **pptx:** таблицы, группы фигур, заметки, заголовок слайда.
5. **docx:** автонумерация и таблицы построчно.
6. **Прочее:** чтение `.xls`, определение кодировки `.txt`, проверка конвертера `.doc` на SberOS.

## 5. Ограничения

- **Сборка PyInstaller** (`make spec`) исключает torch, pandas, sklearn, scipy, matplotlib, transformers, onnx, onnxruntime, langchain и другие. В парсерах их использовать нельзя.
- **Уже доступны:** pymupdf, pypdf, python-pptx, openpyxl, docx2txt, lxml, beautifulsoup4, polars, jinja2.
- **Новые зависимости** — только лёгкие, ставятся через uv с внутреннего зеркала `sberosc.sigma.sbrf.ru`. Каждую согласуй со мной.
- **Целевая машина** — ноутбук на SberOS: Linux, только процессор. Индексация большой папки не должна заметно замедлиться — оцени это.
- **Не трогать** «грабли» из `AGENTS.md`: `batch_size`, `PerformanceMode.LATENCY`, `_ov_token_len` через `count_tokens`, почта выключена.
- **Секреты:** файл `.secret` не читать и не выводить.
- **Парсер** должен остаться генератором `Chunk(idx, text)`. Битый файл не должен ронять индексацию.
- **Тесты:** на каждый формат — юнит-тесты на маленьких синтетических файлах. Сейчас в `tests/` проекта отдельных тестов парсеров нет. Прогон: `make tests` и `make ruff`, либо `.venv/bin/pytest` и `.venv/bin/ruff` в `lib-local-rag-s`.

## 6. Как измерять эффект

**Одно изменение — одна проверка.** Так будет видно, что дала каждая правка.

### Быстро, без полного прогона — на уровне текста и чанков

- Чанки любого файла глазами парсеров проекта:
  ```bash
  LIB_LOCAL_RAG=<проект> daemon-venv/bin/python src/indexer_view.py <файл> --out <папка>
  ```
- Чанки всего корпуса:
  ```bash
  daemon-venv/bin/python src/view_corpus.py corpus
  ```
  **Ловушка:** кэш `work/indexer_view_cache` привязан к sha1 содержимого файла, а не к версии парсера. После изменения парсера его нужно очистить, иначе вернутся старые чанки.
- Метрики текста, которыми подтверждён диагноз:
  - доля текста pptx против полного извлечения python-pptx (таблицы, группы, заметки);
  - число разрывов переносом по регулярке из п. 3;
  - доля чанков МСФО с названием банка и годом;
  - для xlsx — какая строка выбрана заголовком и какие листы пропущены;
  - по запросам `xl000`, `xl003` — есть ли в чанке с ответом название показателя и дата в виде «1 января 2025» или «01.01.2025».

  Предложи, как оформить эти проверки скриптом в стенде (`src/parse_checks.py` или похожий), чтобы запускать их после каждой правки.
- По возможности добавь проверку «ответ есть в индексе»: для ZX Bank и ObliQA в исходных наборах есть эталонные фрагменты, можно проверять, попадает ли их текст в чанки эталонного документа.

### Полный прогон — документные метрики

Около 25 минут. Потеря чанков при первичной индексации сейчас не исправлена и искажает сравнение: число чанков меняется вместе с парсингом. Поэтому прогоняй с обходом дефекта и сравнивай с R7 — это тот же обход на исходном коде:
```bash
cd ~/Downloads/lib-local-rag-eval
LIB_LOCAL_RAG=<проект> .venv/bin/python src/harness.py run --run-id P1 --port 8077 --extra-config "parquet_record_batch_size: 100000000"
.venv/bin/python src/report.py --run P1 --compare R7
```
- Демон запускается из папки проекта, поэтому правки парсеров подхватываются. Интерпретатор — `daemon-venv` стенда, версии из `uv.lock`. `nice` не использовать.
- **Базовые значения R7** (гибрид, полный индекс): nDCG@10 0,684, Hit@1 0,469, Hit@10 0,853, MRR@10 0,609, Recall@10 0,769. xlsx: nDCG@10 0,324, Hit@10 0,273. Сценарий 5: nDCG@10 0,712. Остальные срезы — в `reports/R7.md`.
- **Дооценка.** После правки парсинга в топ-10 появятся новые документы — строка «Неоценённых документов в топ-10» в отчёте. Их нужно оценить асессорами:
  1. `.venv/bin/python src/judge_prep.py postrun --run P1 --modes hybrid --batch 40`;
  2. workflow `src/judge_workflow.js`;
  3. `.venv/bin/python src/judge_merge.py collect / todo / conflicts / merge`.

  Подробности — в `README.md` стенда. Запуск workflow согласуй со мной заранее. Первичную оценку ставь основной моделью: Sonnet в прошлом раунде оказался мягче в зоне релевантности, бинарная каппа по порогу «правильный» всего 0,56. Перед дооценкой пересобери `work/indexer_view_corpus` новыми парсерами (очистив кэш), чтобы асессоры видели новый текст.
